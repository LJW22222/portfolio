2026.07 | 서비스 A(레슨 녹음 AI 피드백 앱) | Spring Boot, JPA, MySQL, 트랜잭션 이벤트, 부하 테스트

배경

서비스 A는 레슨이 끝나면 AI 분석 카드를 만들고 사용자에게 알림을 보냄. 출시 전 부하 감사에서 HTTP 에러는 0%였지만 알림 레코드 일부가 사라짐. 목표는 같은 부하에서 알림 누락 0건.

과제

알림 레코드 8.7%(323/3,719)가 애플리케이션 예외 없이 누락되고 복구 경로도 없었음. HTTP 지표로는 보이지 않아 어디서 빠지는지부터 찾아야 했음.

행동

  • 부하 검증 설계부터 원인 분석, 리스너 재설계, 재측정까지 전담(백엔드 1인)
  • Node.js 부하 테스트로 콜백 API 요청 수와 카드, 알림 row 수를 단계별로 대조해 누락 구간을 특정함
  • 처음 8.7%는 공유 비동기 풀이 포화돼 알림 작업이 거부된 경로가 주였음. 포화 시 커밋 스레드가 직접 실행하게 한 1차 수정은 누락 53%, 알림 저장에 REQUIRES_NEW를 붙인 2차 수정은 누락 33%와 HTTP 에러 59%(커넥션 풀 고갈 정황)로 실패해 되돌림
  • REQUIRES_NEW가 붙은 리스너만 누락 0이라는 대조군과 Spring 문서의 동작을 종합해, 커밋 스레드에서 실행된 알림 INSERT가 이미 끝난 트랜잭션에 참여해 반영되지 않는 경로를 핵심 원인으로 판단함
  • 스레드 풀 튜닝, CDC 릴레이, 별도 outbox 테이블 대신, 리스너 6개에서 @Async를 빼고 BEFORE_COMMIT으로 바꿔 도메인 데이터와 같은 트랜잭션으로 묶음. 외부 발송은 기존 폴링 경로에 그대로 둠
@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
public void handle(CardCreatedEvent event) {
    notificationRepository.save(Notification.pending(event.userId(), event.cardId()));
}

결제 이중 처리 락 경합 해결 및 웹훅 단일 Writer 재설계

2026.04 ~ 2026.06 | 서비스 B(무인 매장 결제 플랫폼, 입사 전부터 운영되던 서비스) | Spring, MyBatis, Redis SET NX 락, PG 웹훅

배경

서비스 B는 주문 누락 CS를 막으려고 결제 콜백과 웹훅을 모두 저장 경로로 두고, Redis 락으로 중복 처리를 막고 있었음. 목표는 결제가 정상이면 사용자도 정상 화면을 보게 하는 것.

과제

PG에서는 결제가 정상 처리됐는데도 3일간 결제 콜백의 61.8%(218/353)가 락 경합으로 에러 화면을 받아 재결제가 생김. 예외 로그는 0건이라 원인이 보이지 않았음.

행동

  • 안전망 설계, 원인 진단, 재설계, 사후 검증 전담(백엔드 1인)
  • 예외가 없다는 점에서 정상 흐름 안의 에러 응답을 의심했고, 남은 로그 한 줄로 하루 85건 중 락 획득 실패 20건이 전부 복구되지 않았음을 확인함
  • 락 실패 때 폴링으로 기다리게 하는 안은 버림. 증상은 사라지지만 두 경로가 같은 데이터를 쓰는 구조가 남기 때문. PG 권장 방향대로 정상 경로에서는 웹훅만 저장하고 콜백은 저장 여부만 확인하게 책임을 나눔
  • 웹훅은 PG 재조회로 결제를 검증한 뒤 저장하고, 주문 생성 실패 시 PG 자동취소로 보상함. 폴링 코드에 처음 붙였던 읽기 전용 트랜잭션이 5초 내내 커넥션을 붙잡게 된다는 점을 코드 리뷰에서 찾아 제거함

Mac mini와 AWS SQS를 활용한 하이브리드 STT 파이프라인 구축

2026.07 ~ 2026.09 | 서비스 A | AWS Lambda, SQS, Transcribe, whisper.cpp, Mac mini

배경

건별 비용을 관측해 보니(2026.05~06, 60초 이상 녹음 100건) AI 분석 원가의 약 80%가 클라우드 STT 비용이었음. 비용은 줄이되 60분 녹음을 10분 안에 처리한다는 목표는 지켜야 했음.

과제

Mac mini 한 대로 전부 처리하면 부하 시뮬레이션에서 10분 목표를 보장할 수 없었음. 비용과 처리 시간을 함께 만족하는 구조가 필요했음.

행동

  • 하이브리드 구조 설계, Mac mini 워커 구현, 용량 검증, 운영 전담(백엔드 1인)
  • SQS로 받은 작업을 Mac mini whisper.cpp 워커(동시 4슬롯)가 처리하고, 라우팅 Lambda가 워커 무응답이나 예상 완료 시간 20분 초과를 감지하면 Transcribe로 자동 전환하게 함
  • 전부 로컬로 처리하는 안은 버림. 시뮬레이션에서 10분 목표를 지키는 동시 처리량이 0건이었기 때문. 무거운 파일부터 Transcribe로 넘기는 방식으로 같은 시뮬레이션(실측 28건의 처리 시간으로 계산, Mac mini 한 대에 한꺼번에 몰리는 최악 가정)에서 동시 18건까지 목표를 지킴
  • 근거 없이 쓰던 처리량 숫자를 실측 처리 속도와 슬롯 수로 다시 계산해 바로잡음

STT 인식 오류율 개선 및 정답지 기반 평가 체계 구축

2026.07 ~ 2026.09 | 서비스 A | whisper.cpp, Python, CER, WER 채점

배경

레슨 녹음에는 소음과 음악이 섞여 클라우드 STT 오류율이 높았고, 품질을 잴 기준도 없었음. 목표는 개선 여부를 숫자로 판정하는 평가 체계를 만들고 그 기준으로 오류율을 낮추는 것.

과제

GPU를 함께 쓰는 동시 실행에서는 같은 구간도 결과가 흔들렸고(같은 3분 구간을 3개 동시에 돌렸을 때 텍스트 14~16% 차이), 확신도 같은 간접 지표로는 실제 정확도를 알 수 없었음.

행동

  • 평가 체계 설계, 오류 원인 분석, 디코딩, 후처리, 라우팅 개선 전담(백엔드 1인). 실험 코드와 반복 측정은 AI 코딩 도구에 맡기고, 정답지를 만든 뒤로는 채택을 정답지 점수로만 판정함
  • 사람이 직접 고친 정답지와 채점기를 만들고, 채택 기준을 실험 전에 정함. 정답지 대부분이 whisper 초안을 고친 것이라 whisper에 유리한 편향이 있음을 감사로 확인해 한계로 기록함
  • 잡음 제거는 버림. 초기 실험에서는 확신도가 올랐지만, 당시 정답지 17구간으로 다시 재니 모두 나빠졌기 때문
  • 음악 녹음의 환각 루프는 디코딩 옵션으로 풀어 한 녹음의 10분 구간 전사가 12자에서 1,345자로 돌아옴. 음악 크기를 재는 게이트는 경로가 바뀐 2구간의 CER을 약 21%에서 13~14%로 낮췄고(실험), 9/15부터 운영에 적용함
  • GPU 읽기, 쓰기 락으로 동시 실행 때 결과가 흔들리던 문제를 줄임. 락을 켠 뒤 당시 정답지 17구간을 4개씩 동시에 다시 돌려도 결과가 같았음(점수 차이 0.00)

배운 점: 좋아 보이는 간접 지표보다, 사람이 고친 정답지와 미리 정한 기준이 채택을 결정해야 함

일하는 방식

  • AI를 검증 체계로 씀. 구현 에이전트와 부하 검증 에이전트의 맥락을 나눠 교차 검증했고, 이 감사에서 HTTP 지표로는 보이지 않던 알림 누락을 찾음. QA 에이전트를 직접 만들어 에이전트 7개로 API 154개를 점검했고, 권한 누락(심각도 높음)을 찾아 고친 뒤 다시 검증함(비참여자 403, 없는 레슨 404). 에이전트는 코드를 고치지 않고 보고만 하며, 무엇을 고칠지는 직접 판단함
  • 앱 개발자와 API 계약을 맞춤. 슬랙으로 계약 변경과 연동 오류를 조율함. v3 전환 때 구버전 전용 API 6개를 정리하고, 폐기한 API의 응답을 410으로 통일했으며, Swagger 문서를 전수 조사함
  • 운영은 지표로 봄. Prometheus, Grafana, Loki로 지표와 로그를 모으고, Slack 알림과 GitHub Actions 배포를 직접 구성함
